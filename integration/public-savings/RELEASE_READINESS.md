## Encrypted backup and isolated recovery

Run `PSS_RECOVERY_TEST=1 node --test apps/web/tests/public-savings-recovery.test.mjs` or `node integration/public-savings/backup-recovery.mjs`. The drill accepts only local synthetic config and source sentinel, snapshots SQL schema/data/routines/triggers, encrypted artifact bytes and evidence/hash keys. It briefly locks writes while taking the dump and invariant snapshot, then releases before restore. It never resets the source database or restores over its three shared seed identities. The only restoration target is `kkisi_public_savings_recovery`; existing targets require the same installation sentinel. Unknown target names/sentinels fail closed.

A real MariaDB11.4 drill passed on 2026-10-29: 17 tables, 48 rows, 3 routines and 5 triggers matched; 462 encrypted artifacts matched byte-for-byte and all 462 decrypted with the restored evidence key. Counts describe that snapshot and change as tests add records. Two recovery tests passed without skips. Backup SHA-256: `7cec3c40d3f41ad9cb5b785d4f1ec5a4c42e88543c14cf50a1b12f20c1baf66f`. This is restoration of synthetic data, **not production restoration acceptance**.

Private `.local/public-savings/recovery/<run>/` holds `backup.aes256gcm`, its separate `backup-key.bin`, `manifest.json`, restored artifacts and `restored-evidence-keys.json`. Directories are0700 and files0600. The manifest binds encrypted SQL/artifact digests, row digests and evidence-key fingerprint to the backup/key files without printing secrets. Database CLI passwords are supplied via stdin into a temporary0600 defaults file removed in `finally`; no secret appears in process arguments or stdout. Backups contain no global environment files, production records or administrative credentials. Preserve encrypted artifacts **and** the associated evidence/hash keys: a database dump alone cannot reconstruct private proof. This local co-location supports a drill only; actual deployment requires separately controlled key escrow, access audit, geographic backup custody, retention/legal holds and a restore from that custodian.

## Rollout gates and rollback

1. Keep public intake disabled until current actual legacy schema/SQL-mode/index/trigger/grant metadata and **every** financial writer have been checked against the controlled commands. Bind console actor roles and branch authority to authenticated server sessions; local operator credentials are synthetic. Confirm actual PHP proof/print hooks through the current legacy evidence register.
2. Verify the additive migration checksum/preflight and interrupted migration recovery against an isolated replica first (`node integration/public-savings/preflight.mjs`, `pnpm pss:migration:verify`). Never run representative `schema.sql` over actual legacy tables. Take approved DB/object/key backups before any actual migration; verify restoration in a separate authorized environment. Obtain grants for runtime, legacy writer, worker and maintenance identities independently.
3. Configure verified roster/contact provenance, authoritative payroll/calendar/holidays and operations/supervisor branch recipients. Verify real provider sender/template approval, credentials, TLS, timeouts, idempotency, retries, dead letters and callbacks. Capture delivery and local contract servers do not prove real delivery. Confirm private object-store storage, key rotation/custody and read authorization; private evidence must not enter public URLs or logs.
4. Local activation uses `PSS_LOCAL_STAGING=1`, matching sentinel and loopback boundary; `PSS_INTAKE_ENABLED=0` pauses new issuance/submission while preserving proof/receipt access. These local flags do not activate an actual deployment. Default fail-closed behavior must remain until the separately reviewed deployment adapter exists.
5. Before pilot, run full relevant regressions/typecheck/lint/build, real SQL concurrency/rollback tests, authenticated role/branch negative tests, provider/object-store failure recovery, and responsive browser scenarios. Obtain actual member/staff acceptance, physical mobile/WhatsApp/Safari and accessibility checks, holiday/cutoff and first-enrollment/duplicate/cross-channel acceptance. Record actual-runtime outcomes separately from local/headless tests.
6. Rollback means intake OFF, preserve committed requests/evidence, continue safe receipt recovery and outbox investigation/drain. Never delete applications, drop auxiliary tables, disable guards or revert financial records to undo release. Failed notifications must not resubmit financial intake. Reconcile before reopening; resolve uncertain commit outcomes through the original idempotency identity.
7. Monitor reconciliation counts, job age/retries/dead letters, consumed-link/application/header/reservation consistency, proof integrity, stale staff reviews and provider failures. Schedule retention and escalation using separately scoped operators. Alert actual named operations owners; define acceptable queue lag, response targets, restoration RPO/RTO and holiday staffing before pilot. Local polling/counts do not establish production monitoring or incident ownership.

Actual-runtime acceptance remains open wherever the current evidence register lacks approved runtime results: all-writer enrollment, authenticated role/branch binding, real provider delivery, deployed private object/key custody and restoration, operational calendar/contact provenance, TLS/redacted logging and staffed pilot sign-off. Source retrieval or synthetic SQL tests alone do not close those gates.
