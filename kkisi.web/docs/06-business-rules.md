# Phase 6 — Business Rules & Logic

## 6.1 Multi-Company / Branch Isolation

- Every data record is stamped with `company_id`
- **Role 1–2 (Super Admin):** Can see all companies in dropdowns and reports
- **Role > 2 (Branch Staff):** Data automatically filtered to their assigned `company_id` from session
- `categori_company()` helper reads the current company's `category` field to conditionally alter behavior

## 6.2 Member Credit Limit Rules

### For Toko (Store Credit)
```
effective_limit = (gaji_minus > 0) ? gaji_minus : limit_toko

monthly_usage = SUM(db_sales.grand_total)
                WHERE nik_kar = member.nik_kar
                  AND payment_type = 'Kredit'
                  AND sales_status = 'Final'
                  AND sales_date within CURRENT MONTH

remaining_credit = effective_limit - monthly_usage
```

**Rules:**
- Credit resets monthly (current calendar month only)
- `gaji_minus` overrides `limit_toko` when active — this represents a salary-deduction scenario
- `status_anggota` must be `AKTIVE` to transact (PENSIUN/RESIGN shown as warning)

### For PPOB Credit
```
ppob_monthly_usage = SUM(orders.order_amount)
                     WHERE nik_kar = member.nik_kar
                       AND payment_method = 'pay_by_wallet'
                       AND order_status = 'delivered'
                       AND ppob = 1
                       AND created_at within CURRENT MONTH

ppob_remaining = limit_ppob - ppob_monthly_usage
```

## 6.3 Kasir (Cash Register) Session Rules

1. A user must **open a kasir** before accessing POS for that day
2. `cek_buka_kasir($company_id)` checks for an **open session (status=1) today** for the current user
3. Each kasir has an `saldo_awal` (opening cash balance)
4. On close (`tutup_kasir`):
   - `saldo_akhir` = saldo_awal + cash received from sales
   - `saldo_kredit` = total credit sales amount
   - `tgl_tutup` set to NOW()
   - `status` set to 0
5. Sales are linked to the kasir session via `db_sales.id_kasir`

## 6.4 PPOB Product Rules

PPOB items are regular `db_items` entries with:
- `ppob = 1` flag
- `ppob_type` ∈ `{pulsa, data, pln}`
- `paket_data` — data package size for filtering

**Operator Detection (Pulsa/Data):**
- Phone number must be ≥ 10 digits
- Calls IAK API `check_operator()` to identify carrier
- If `rc = '00'` → valid, proceed to product list

**PLN Validation:**
- Customer/meter number must be exactly 11 digits
- Calls IAK `inquiryPLN()` → validates meter
- If `status = '1'` → valid

## 6.5 Invoice Code Generation Rules

|--------|--------|---------|
| POS Sales | `INV{ymd}{05d}` | `INV2406150001` |
| PPOB | `PPOB{ymd}{05d}` | `PPOB2406150001` |

The counter resets each month (based on `MONTH` + `YEAR` filter on the table).

## 6.6 Tax Calculation Rules

### Inclusive Tax
```
tax_amount = amount / ((tax_rate/100) + 1) / 10
```
*(Note: the `/10` seems like a domain-specific scaling factor — possibly per unit of 10)*

### Exclusive Tax
```
tax_amount = (amount × tax_rate) / 100
```

**Round-off:** If `db_sitesettings.round_off = 1`, grand_total is rounded to nearest integer.

## 6.7 Payment Type Rules

- **Cash:** Immediate settlement; `paid_amount = grand_total`; change_return calculated
- **Kredit:** Deferred payment; tracked against customer due balance or member limit
- **Depo:** Purchase from depot/distributor (specific to purchase module)
- Payment types managed in `db_paymenttypes` table

## 6.8 Stock Management Rules

### Stock In (Purchase)
```
db_items.stock += purchase_qty
db_stockentry INSERT (type='purchase', reference_id=purchase_id)
```

### Stock Out (Sale)
```
db_items.stock -= sale_qty
db_stockentry INSERT (type='sales', reference_id=sales_id)
```

### Return Stock
```
Sales Return: db_items.stock += returned_qty
Purchase Return: db_items.stock -= returned_qty
db_stockentry INSERT (type='return')
```

### Stock Adjustment (Penyesuaian Stok)
```
db_items.stock = new_qty
db_stockentry INSERT (type='adjustment')
```

### Stock Opname Approval
```
db_items.stock = qty_actual  (replaces system quantity)
db_stockentry INSERT (type='opname')
```

## 6.9 Loan Installment Rules (Koperasi Module)

1. **Flat rate** loans — interest spread equally across all installments
2. Installment schedule generated by `get_bungan_bulanan($doc_no)`:
   - Starting from `awal_pinjaman` (or `doc_date + 1 month` if null)
   - Monthly on `tgl_tempo` day of each month
   - `n` installments = `plan_jangka_waktu` (tenor in months)
3. **Auto-payroll deduction:** `get_update_cicilan()` marks past installments as `Bayar` with `type_cicilan='PAYROLL'`
4. **Loan completion:** When last installment = 'Bayar', `status_bayar` set to `LUNAS`
5. **Gaji Minus** (salary deduction loan) — referenced via `bank_pembiaya='GAJI MINUS'` — affects member's `limit_toko`

## 6.10 Mobile Order Lifecycle

```
pending → confirmed → processing → ready_to_take → delivered
    │                                                    │
    └──────────────── returned ──────────────────────────┘
    └──────────────── canceled
```

- `Sales_mobile::update_status()` handles transitions
- `delivered` orders are counted in revenue; `returned`/`canceled` are not
- Mobile orders can be "processed" as POS sale via `pos_update`

## 6.11 SMS Notification Rules

Templates in `db_smstemplates`:
| Template ID | Name | Trigger |
|------------|------|---------|
| 1 | GREETING TO CUSTOMER ON SALES | After POS sale finalized |
| 2 | GREETING TO CUSTOMER ON SALES RETURN | After sales return |

**Conditions to send SMS:**
1. `is_sms_enabled()` = true (db_company.sms_status = 1)
2. `customer_id != 1` (not walk-in/anonymous)
3. Customer has non-empty `mobile` field

**Template variables:** `{{customer_name}}`, `{{sales_id}}`, `{{sales_date}}`, `{{sales_amount}}`, `{{paid_amt}}`, `{{due_amt}}`, `{{company_name}}`, `{{company_mobile}}`, `{{company_address}}`, `{{company_website}}`, `{{company_email}}`

## 6.12 Report Calculation: Laporan Toko (Branch P&L)

```
Persediaan Awal = Opening inventory value (purchase_price × stock at month start)
+ Pembelian Depo  = Purchases with payment_type='Depo' this month
+ Pembelian Cash  = Purchases with payment_type='Cash' this month
+ Pembelian Kredit = Purchases with payment_type='Kredit' this month
= Total Persediaan

- Penjualan = Total sales grand_total (status=Final) this month
= HPP (COGS) = SUM(purchase_price × qty_sold) this month

Laba Kotor = Penjualan - HPP
- Biaya Operasional = SUM(db_expense.amount) this month
= Laba Bersih
```

## 6.13 Konsinyasi (Consignment) Rules

- Separate flow from regular purchase: `Purchase::konsinyasi` / `Purchase::add_konsinyasi`
- `purchase_type = 'Konsinyasi'` in `db_purchase`
- Stock received separately from payment — paid only on sale
- Separate return flow: `Purchase_return::konsinyasi`
- Separate invoice format: `invoice_konsinyasi()`
