# Sales Return (Retur Penjualan) — Audit and Implementation Handover

Date: 6 October 2026

Status: implemented locally and verified against the replicated local staging database (`kkisi-staging`, MariaDB 11.4, `STRICT_TRANS_TABLES`). Production writes are **disabled** (`SALES_RETURN_WRITES_ENABLED=0`); the production database account has not been created.

Constraint kept: no new table, column, index, view, trigger or database. Only the existing `db_salesreturn`, `db_salesitemsreturn` and `db_salespaymentsreturn` tables are written, plus `db_sales.return_bit` and `db_items.stock`.

## 1. Legacy audit

The legacy module is `Sales_return` / `Sales_return_model` (CodeIgniter). It is reached from Sales list → Action → Sales Return, never from the POS screen.

| Legacy behaviour | Evidence | Consequence |
|---|---|---|
| Header + lines + optional refund payment, `db_sales.return_bit = 1`, stock recomputed with `Pos_model::update_items_quantity()` | `verify_save_and_update()` | Kept: same tables, same flag, same stock ledger |
| Stock is a ledger: opening + purchases **+ sales returns** − purchase returns − sales (`year(return_date) >= 2025`) | `Pos_model.php:1033` | Every return row counts for stock automatically, so the cached `db_items.stock` must move by exactly the returned quantity (done; verified in the same transaction) |
| Register detail subtracts returns by `id_kasir`, `payment_type` (`Cash`/`Kredit`) and `return_status = 'Return'`; `tutup_kasir` ignores returns | `modal_detail_buka_kasir.php`, `Pos::tutup_kasir` | Next.js fills `id_kasir`, `payment_type`, `return_status='Return'`; Next.js register close now subtracts Cash refunds |
| Profit & loss subtracts `db_salesreturn.grand_total` from sales | `report-profit-loss.php` | The original sale must stay unchanged; changing `db_sales.grand_total` would subtract twice |
| Member credit and payroll reports read `db_sales.grand_total` only | `tagihan_anggota()`, `Reports_model` monthly Kredit | Legacy screens do not see Kredit returns (see finding F5) |

### Fatal findings in the legacy flow

| # | Finding | Impact | Resolution in Next.js |
|---|---|---|---|
| F1 | The insert never sets `pos`, `payment_type`, `id_kasir` and most `db_salesitemsreturn` NOT NULL columns, and writes `'Paid'/'Unpaid'` into the **INT** column `db_salesreturn.payment_status` | Under `STRICT_TRANS_TABLES` (staging; MariaDB 10.11 default) every legacy return insert fails. The production dump has **0 return rows** ever | Every NOT NULL column is written explicitly; `payment_status = 1` (settled) |
| F2 | `ALTER TABLE db_salesreturn AUTO_INCREMENT = 1` inside the save transaction | DDL commits the open transaction implicitly; the save is not atomic | No DDL; one transaction with retries |
| F3 | Return code reads `sales_return_init` **without a branch filter** and numbers by global `MAX(id)+1` | Every branch receives the first branch's prefix; concurrent saves collide | Per-branch code `sales_return_init + yyMMdd + 5-digit monthly sequence`, under the branch lock, collision-checked. Lengths differ from legacy codes (`init + 4 digits`), so they never collide |
| F4 | No check of returned quantity against sold minus already returned; one return per sale, then edit = delete + reinsert | Units can be refunded twice; edits silently rewrite history | Immutable returns, several partial returns per sale, remaining quantity validated on locked rows |
| F5 | Kredit returns never reduce `tagihan_anggota()` or the monthly Kredit/payroll report | A returned Kredit purchase is still deducted from salary in legacy reports | Next.js credit usage (POS limit, receipt limit) subtracts Kredit returns. The external payroll generator is patched by the payroll admin; Kredit returns go live without waiting for it (owner decision, gate G3) |
| F6 | All queries interpolate raw input (`where id='$id'`) | SQL injection | Parameterized queries only |
| F7 | `db_salesreturn` / `db_salesitemsreturn` have no index on `sales_id` / `return_id` | Full scans as returns grow | Tables are empty today and returns are rare; acceptable. Recommend `idx(sales_id)` / `idx(return_id)` as a separate approved schema change |

Payroll source (found after the first audit): `trans_tagihan` only covers PPOB, but store Kredit is deducted through `trans_potongan_bulanan` (header per period and group: `ANGGOTA`/`BMP`/`KOPERASI`, `doc_status` OPEN → APPROVED) and `trans_potongan_matrix` (per NIK, columns `TOKO_TAMBUN`/`TOKO_MJ`/`TOKO_GIIC`). Period `POT202609…` (created 2026-09-28) holds exactly the August Kredit sales per NIK (1346/1346 rows match `SUM(db_sales.grand_total)` for branch 1). It is generated by a separate application that is not in this repository and ignores `db_salesreturn`. Because the snapshot of month M is taken late in month M+1, the same-month Kredit rule is always before that snapshot. Fixing F5 automatically means changing that generator (gate G3).

## 2. Business rules (server-side, re-checked on locked rows)

- A return references one saved sale of the active branch (`ppob = 0`, `Final`, `status = 1`, payment `Paid`/`Dibayar`, method Cash/QRIS/Kredit).
- The saved totals must be reconstructible: lines of this branch only, active, no tax, no transaction discount, `Σ line total = subtotal = grand_total`, paid ≥ total. Otherwise `LEGACY_TOTALS_UNSUPPORTED`.
- Window: **Cash/QRIS** — sale day through 7 calendar days after it (Asia/Jakarta), across months. **Kredit** — only within the sale's calendar month (fallback for the missing payroll status). Expired → `RETURN_WINDOW_EXPIRED` / `CREDIT_PERIOD_CLOSED`.
- Quantity per item ≤ sold − every earlier return row of that sale (whatever wrote it).
- Refund amount = cumulative allocation of the saved line total, so partial returns always sum to the saved total exactly (whole rupiah for whole-rupiah lines; BigInt arithmetic).
- Refund channel: Cash and QRIS sales → cash from the drawer (`payment_type = 'Cash'`); Kredit → reduces the member's monthly credit usage (`payment_type = 'Kredit'`).
- The cashier's own register session of today must be open (`id_kasir` is mandatory). Cash refunds may not exceed the drawer: opening balance + session Cash sales − session Cash refunds (`DRAWER_INSUFFICIENT`).
- Items in stock opname (`status_so = 1`) are refused (`STOCK_OPNAME`), as in checkout.
- Reason is mandatory (3–200 printable characters; tables are latin1).
- Permission `sales_return_add` (API guard **and** inside the transaction); viewing needs `sales_return_view` or `sales_return_add`.
- Idempotent: `reference_no = NXR-<sha256(company:user:key)>`; a replay returns the saved return, a different payload under the same key is `IDEMPOTENCY_CONFLICT`.

## 3. Database flow (one transaction, READ COMMITTED, deadlock retry of the whole transaction)

Lock order is the same as checkout and register close, so they serialize on the branch row and never deadlock:

1. `db_company` FOR UPDATE (branch mutex, `sales_return_init`)
2. `db_users` + role + `sales_return_add` FOR UPDATE
3. idempotency lookup on `db_salesreturn.reference_no`
4. `db_sales` row FOR UPDATE (serializes all returns of the sale), lines of `db_salesitems`, earlier `db_salesitemsreturn`
5. own open `db_buka_kasir` FOR UPDATE; drawer check for Cash
6. `db_items` FOR UPDATE (ORDER BY id)
7. INSERT `db_salesreturn`, `db_salesitemsreturn`, `db_salespaymentsreturn`
8. `UPDATE db_items SET stock = stock + qty` (guarded by branch and `status_so = 0`)
9. `UPDATE db_sales SET return_bit = '1'`

Written values follow the legacy readers: `return_status = 'Return'`, `status = 1`, `pos` copied from the sale, `return_date` = local Jakarta datetime, `id_kasir` of the session, `purchase_price` from the sale line (HPP at sale time), `item_type` from the sale line, `system_name = 'Next.js POS'`.

Related changes:

- **Register close** no longer refuses sessions containing returned sales. Expected drawer cash = opening + Cash sales − Cash refunds of the session (legacy "Total Uang Tunai"); `saldo_kredit` keeps the legacy `tutup_kasir` meaning. The recap shows Cash/Kredit refunds and net Total Sales. Session returns are identified by branch + till + owner + time window (`db_salesreturn` has no session column; a user holds at most one open session). They are read through the read-only client **after** the branch lock is held: every return writer holds that lock until commit, so the read is complete and the register account needs no new privilege.
- **Credit limit** (POS member lookup, checkout limit check, checkout receipt) subtracts Kredit returns of the month's Kredit sales, through the read-only client. A read that misses a just-committed return only lowers the remaining limit, never raises it, so the checkout account (`kkisi_pos_runtime`) keeps its exact privileges.
- **Reprint**: `return_bit = '1'` is now eligible (the saved sale is never modified); the reprint states that items were returned. Other unknown markers stay blocked.

## 4. UI

- Sales detail: "Retur barang" (only with `sales_return_add` and an eligible sale), a "Retur penjualan" section with the window, blocking reasons and earlier returns.
- `/sales/invoice/{id}/return`: per-line steppers capped at the remaining quantity, preset and free-text reason, live refund preview, a review step stating the cash to hand over or the credit reduction, explicit confirmation. Lines become cards below 600 px.
- `/sales/returns` list (date range ≤ 93 days, search), `/sales/returns/{id}` detail, `/pos/return-receipt/{id}` 80 mm nota retur. Sidebar "Retur Penjualan" for `sales_return_view`.
- API: `GET/POST /api/sales/{id}/returns`, `GET /api/sales/returns`, `GET /api/sales/returns/{id}`; POST requires CSRF.

## 7. Gates before production activation

1. **G1 single writer** — same blocker as checkout (GCP_PARTIAL_CUTOVER §9): legacy PHP and Next.js must not both operate a pilot branch.
2. **G2 account** — create the production return account from the reviewed SQL (support ticket if cPanel cannot run table/column grants); never ALL PRIVILEGES.
3. **G3 Kredit in payroll — owner decision 2026-10-06: Kredit returns are enabled together with Cash/QRIS in production.** The payroll admin will patch the separate payroll generator so that the store deduction (`trans_potongan_matrix.TOKO_*`) of month M subtracts that month's Kredit returns, for example:
   ```sql
   SUM(s.grand_total) - COALESCE((SELECT SUM(r.grand_total) FROM db_salesreturn r
     WHERE r.sales_id = s.id AND r.payment_type = 'Kredit' AND r.return_status = 'Return' AND r.status = 1), 0)
   ```
   Until that patch is live, check every payroll document for members with Kredit returns (list: `/sales/returns`, method Kredit) before it is APPROVED. Legacy `tagihan_anggota()` (legacy POS remaining limit) also ignores returns; this only matters for branches still selling through the legacy POS.
4. **G4 register** — returns must be processed on sessions opened and closed in Next.js (legacy `tutup_kasir` ignores refunds).
5. **G5 acceptance** — one committed end-to-end return per method on staging with synthetic data, physical 80 mm print, then register close.

## 8. Rollback

Code-only: revert the return routes/components and the register/credit/reprint changes; disable with `SALES_RETURN_WRITES_ENABLED=0` (the page then shows that saving is not enabled and the API answers 503). Return rows already written are business records and stay; they keep counting in the legacy stock ledger, P&L and register detail exactly as legacy-written returns would. Account rollback: `DROP USER` (access only).
