Public may INSERT compatible OPEN headers and immutable evidence, never update legacy deduction/profile/configuration. ## 1. Invariants and trust boundary

1. One token commits at most one existing business request with exactly one required DB notification set and immutable audit/outbox intent. Exact retry returns the same receipt; changed retry conflicts. This is a PUBLIC invariant, separate from cross-channel business uniqueness.
2. One agreed pending business conflict key has at most the owner-approved number of pending requests **across every channel**. Candidate key/scope and terminal release rules await B-05; no permanent NIK-only UNIQUE or assumed per-period policy.
3. A PUBLIC submitted body/member/type/old/new/requested-period/consent/signature snapshot cannot be changed by Laravel edit/cancel or unapproved CI2 paths. Corrections follow signed policy: permitted rejection plus new request/fresh consent, never rewriting proof or reopening consumed token. Rejecting APPROVED is not a payroll reversal.
4. One authorised canonical processor wins a permitted transition. Its master/member/header/audit effects are consistent and atomic for the protected scope. Concurrent approve/reject/cancel/replay cannot leave changed payroll with rejected/unchanged header, two effective approvals, or mixed member/master amounts.
5. Proof/template/storage references remain immutable and private. If correct public PDF/READY is a prerequisite, bypass through direct CI2 URLs must be prevented before processing; manual observation is insufficient.
6. Existing legitimate MOBILE operations continue within their own approved identity/state boundaries; no blanket route shutdown, global serialization of unrelated members, silent financial-policy change or Next payroll ownership takeover.

Trusted origin resolves from immutable aux binding to request PK plus approved writer identity/control, not client `is_mobile`, prefix, unknown doc_no or encrypted doc_no. Header doc_no has no observed unique constraint; any legacy doc_no-based lookup requires exactly one row or failclosed before processing. Aux origin binding and request commit together; no published row without its guard metadata. SQL grants alone do not implement per-row origin authorization; same shared DB account cannot be treated as distinct authenticated channels without proven additional controls.

A fail-before-first-write design and one atomic processor unit (or proven equivalent enforcement across every effect) are mandatory. Model14A shows why a partial guard is insufficient; production runtime settings/hidden controls remain unknown.

## 4. Proposed atomic command protocol (not implemented)

Approved actor/channel → stable member identity + exact requestPK/origin → acquire canonical member/conflict-key reservation → lock link/request/config in fixed order → check purpose/contact/version/eligibility/amount/period/current state and requested action → check exactly one target/config or approved new enrollment → check snapshot/required artifact readiness → execute whole command transaction → persist attributable command audit/idempotency result → commit → aftercommit delivery. All participating transactional effects remain on one physical DB connection.

For PUBLIC submit: durable private signature stage first; then one UoW inserts request, mandatory notif, immutable audit/snapshot/job intents and consumes link with receipt. No HTTP/file decode/PDF render/provider call inside locks. Aftercommit PDF/mail failure leaves OPEN+CONSUMED; retry only the artifact/delivery. A lost response resolves outcome from authoritative primary and original command key, never blindly resubmits.

For processing: this is a **required contract for the protected legacy processor**, not a new Next API. Consumed token does not authorise approval. A request/key reservation must last across the **whole** process command, including member/master writes; statement locks released between autocommits are insufficient. Request edit/cancel/state races require locked current-state checks and versioned conditional outcomes for every writer. Do not invent a version column already present; adding any guard metadata requires future approved schema/control design.

Contact OTP11 verifies approved contact control; final consent/signature binds reviewed snapshot. It is not automatically a transaction-specific OTP or independent MFA. B-10 must decide if final-payload OTP is required; then return to challenge contract design before implementation. Never imply the existing temporary-token mobile verification is safe to reuse.

## 6. Stop / recovery

Unknown commit, origin/body mismatch, duplicate reservation violation, unexplained payroll/header divergence, unsupported trigger effects or wrong proof blocks activation. After future activation, any such event stops new public intake under approved runbook; retain committed rows/consumed tombstones/private proof, alert owner, reconcile authoritative facts. Do not delete duplicates, auto-reverse payroll, reopen links, silently reject records or enable a competing Next processor. Current checkpoint does not change any flag/service/account.
