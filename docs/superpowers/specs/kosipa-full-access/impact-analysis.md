# Impact analysis — `kosipa-full-access`

| Area | Impact | Risk | Mitigation |
|---|---|---|---|
| **Frontend** | New forms, dialogs and action bars on existing KOSIPA pages (members, savings, loans, payroll) and new areas (masters, exit, SHU, requests, access grants). Existing read pages stay; actions render from server capability + state | Medium: UI must never imply authority (hidden button ≠ control); large forms (loan, payroll adjustments) | Reuse `components/console/kosipa/*`, `CurrencyInput`; server re-checks; WCAG AA (NFR-106); `router.refresh()` after commands |
| **Backend** | ~40 command use cases, 7 writer repositories, command pipeline, ownership gate, grants, ledger | High: financial correctness, concurrency | Pure domain rules (existing + new), one transaction per command, lock order, idempotency, characterization + reconciliation before activation |
| **Database** | Writes to 30+ legacy tables shared with PHP, TOKO and smartkkisi; proposed additive objects: `kosipa_command_ledger` (FD-01), Tier-1 indexes and unique `doc_no` (FD-02); console store table for grants | High: shared live DB, no constraints, legacy readers | No DDL without decision; legacy-compatible values (REQ-142); production changes only by operator-run reviewed SQL (OD-4); additive with `DROP` rollback |
| **Auth / tenant scope** | New write capabilities, grant store, maker-checker; KOSIPA stays cooperative-wide (no branch) | High: privilege escalation, identity link misuse | Identity link grants nothing for writes; self-grant refused; security matrix (08 §6) |
| **Queues / workers** | Post-commit side effects (notifications, PDFs) via outbox; payroll approval chunked inside one transaction | Low/Medium | Reuse `pss_outbox` pattern; no IO inside transactions |
| **Security** | Removes client-trusted money/status paths for migrated features; legacy risks remain until switch-off (private register) | Medium | Legacy switch per feature (FD-03); private findings stay private |
| **Performance** | New locks on member/document rows; payroll approval touches up to a month of instalments | Medium: lock contention with PHP during transition, 1.2 M-row table without index | Single writer per feature; indexes (FD-02); chunked updates; `capLockWait`; baselines then targets |
| **Capacity** | Up to 7 writer pools within a full 12-connection budget | High until B5/B8 decided | Pools ≤ 2, only enabled writers count, activation order is the capacity plan (existing guard) |
| **Deployment** | Feature flags per context; operator SQL for writer accounts, ledger, indexes, switch; console store in production (B6) | Medium | Runbook in [11](11_CUTOVER_AND_ROLLBACK_PLAN.md); rehearsals on staging; rollback ≤ 15 min |
| **Other applications** | TOKO Kredit limits and member status, smartkkisi wallet/token/request status, legacy payroll procedure all read rows Next.js will write | High | Compatibility contracts (07 §6) + compatibility tests (gate 4); TOKO `Member` menu off at C-2; smartkkisi contract FD-08 |
| **Data quality** | Existing anomalies (corrupted members, duplicates, divergent statuses, auto-paid instalments) are visible but not corrected | Medium | Reported for finance (MIG-102); commands refuse to act on ambiguous rows with a clear code |
| **Mock data** | Not applicable: this repository has no `packages/data` mock layer; KOSIPA reads use the live/staging adapter. Synthetic databases are used for destructive tests | — | MIG-108 |
| **Layers touched** | `packages/domain` (rules), `packages/application` (commands), `apps/web/src/infrastructure` (writers, gate), `apps/web/src/app` (API/pages), `apps/web/db` (proposed DDL), `docs/migration/sql` (review-only SQL) | — | Layering rule `apps → application → domain` kept |
